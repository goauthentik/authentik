[KEDA](https://keda.sh/docs/2.21/) can scale authentik servers on CPU usage and workers on queued tasks.

A [ScaledObject](https://keda.sh/docs/2.21/reference/scaledobject-spec/) specifies the Deployment and scaling metric; KEDA creates a Horizontal Pod Autoscaler (HPA) for it. Disable the chart's HPA for any Deployment managed by KEDA so that two HPAs do not compete. For CPU-only server scaling, use the [chart HPA](./hpa.mdx) instead.

## Prerequisites

- An existing authentik [Helm chart installation](../../../install-config/install/kubernetes.mdx) and its `values.yaml` file.
- For server CPU scaling, a working resource-metrics API, usually provided by [Metrics Server](https://kubernetes-sigs.github.io/metrics-server/). Every container in the server pods needs a CPU request for [pod CPU utilization](https://keda.sh/docs/2.21/scalers/cpu/#prerequisites) to be defined.
- For worker queue scaling, a Prometheus query endpoint that KEDA can reach and that contains authentik's [worker metrics](../monitoring.mdx#metrics). This example uses an existing [Prometheus Operator](https://prometheus-operator.dev/docs/getting-started/installation/) to scrape the chart's `ServiceMonitor`. The authentik metrics endpoint alone is not enough.

## Install KEDA

If needed, [install KEDA](https://keda.sh/docs/2.21/deploy/). This command installs the chart version currently available from the repository. Check compatibility with your Kubernetes cluster using the documentation for your installed KEDA version.

```shell
helm repo add kedacore https://kedacore.github.io/charts
helm repo update
helm install keda kedacore/keda --namespace keda --create-namespace
```

## Configure the Helm chart

Merge these `server` and `worker` settings into your existing `values.yaml`; keep the rest of your configuration.

```yaml title="values.yaml (excerpt)"
server:
    replicas: 2
    autoscaling:
        enabled: false
    resources:
        requests:
            cpu: 500m
worker:
    replicas: 1
    autoscaling:
        enabled: false
    metrics:
        enabled: true
        serviceMonitor:
            enabled: true
```

With the chart defaults and release name `authentik`, `worker.metrics.enabled: true` creates a `ClusterIP` Service named `authentik-worker-metrics` on port 9300. The ServiceMonitor specifies `/metrics` as the scrape path. Keep the unauthenticated metrics Service internal.

Prometheus must select the ServiceMonitor's namespace (by default, the authentik namespace) through `serviceMonitorNamespaceSelector`. A null selector searches only the Prometheus resource's namespace. `serviceMonitorSelector` must match the ServiceMonitor's labels; set `worker.metrics.serviceMonitor.labels` if needed.

When switching from the chart HPA, disable it before applying the ScaledObjects. Without the chart HPA, Helm writes `spec.replicas` from `server.replicas` and `worker.replicas`. The handoff and later Helm upgrades can briefly reset KEDA-managed replica counts. Set these values near expected counts and check capacity after upgrades. If KEDA manages only one Deployment, leave the other's HPA settings unchanged.

## Configure the ScaledObjects

Save each ScaledObject in its own file, in the same namespace as its target Deployment. These examples use `authentik-server` and `authentik-worker` in `default`. Adjust the names and namespaces (including the worker query's `namespace` selector) to match your installation. Tune replica limits and thresholds for your workload.

### Server CPU usage

This trigger targets 75% of requested server pod CPU (375m for a 500m request if the pod has only the authentik container). CPU alone cannot scale up from zero replicas.

```yaml title="server-scaledobject.yaml"
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
    name: authentik-server
    namespace: default
spec:
    scaleTargetRef:
        name: authentik-server
    minReplicaCount: 2
    maxReplicaCount: 5
    advanced:
        horizontalPodAutoscalerConfig:
            behavior:
                scaleDown:
                    stabilizationWindowSeconds: 300
    triggers:
        - type: cpu
          metricType: Utilization
          metadata:
              value: "75"
```

### Worker queued-task count

`authentik_tasks_queued` counts tasks in the `QUEUED` state by queue and actor. It includes already-enqueued tasks scheduled for later (`eta`), but excludes tasks in progress, those waiting for dependencies, and recurring runs not yet enqueued. If delayed tasks are common, consider a signal that measures work due now instead.

Each worker exports the shared queued-task count. The query takes the maximum per queue and actor before summing, so scraping multiple workers does not count the same tasks more than once.

This example queries a Prometheus Service named `prometheus` in the `monitoring` namespace. Set `serverAddress` to your Prometheus endpoint.

```yaml title="worker-scaledobject.yaml"
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
    name: authentik-worker
    namespace: default
spec:
    scaleTargetRef:
        name: authentik-worker
    minReplicaCount: 1
    maxReplicaCount: 5
    advanced:
        horizontalPodAutoscalerConfig:
            behavior:
                scaleDown:
                    stabilizationWindowSeconds: 300
    triggers:
        - type: prometheus
          metadata:
              serverAddress: http://prometheus.monitoring.svc:9090
              query: 'sum(max by (queue_name, actor_name) (authentik_tasks_queued{namespace="default",service="authentik-worker-metrics"}))'
              threshold: "20"
              ignoreNullValues: "false"
```

Adjust the `namespace` and `service` selectors if your Prometheus series use different labels. Workers normally publish zeros for registered actors when the queue is empty.

If the query returns no series, `ignoreNullValues: "false"` makes KEDA report an error. Missing one worker's scrape might still leave matching series, so monitor Prometheus target health. If Prometheus requires authentication, configure a KEDA [TriggerAuthentication](https://keda.sh/docs/2.21/concepts/authentication/).

With KEDA's default `AverageValue` metric type, `threshold: "20"` targets about 20 queued tasks per replica. A count of 100 calls for about five replicas, subject to HPA behavior and `maxReplicaCount`. Tune the threshold to one worker replica's throughput.

## Deploy and verify

Upgrade your Helm release with the updated `values.yaml`. This command assumes a release named `authentik` in the `default` namespace; adjust both to match your installation:

```shell
helm upgrade authentik authentik/authentik --namespace default -f values.yaml
```

If scaling workers, check that the `ServiceMonitor` exists:

```shell
kubectl get servicemonitor authentik-worker -n default
```

Before applying the worker ScaledObject, check in Prometheus that the worker targets are UP and the query above returns one value. A ServiceMonitor alone does not confirm that Prometheus scraped the metrics.

Apply the ScaledObjects and inspect the HPAs that KEDA creates. If scaling only one Deployment, omit the other file and its HPA inspection command:

```shell
kubectl apply -f server-scaledobject.yaml -f worker-scaledobject.yaml
kubectl get scaledobject,hpa,deployment -n default
kubectl describe hpa keda-hpa-authentik-server -n default
kubectl describe hpa keda-hpa-authentik-worker -n default
```

For worker scaling, watch `kubectl get deployment authentik-worker -n default --watch` as tasks enter and leave the queue. For CPU scaling, watch `kubectl get deployment authentik-server -n default --watch` under server load.

## Capacity and tuning

- Keep at least one worker for scheduled tasks and file monitoring. To provide worker redundancy, use at least two replicas on different nodes. Two server replicas help with [availability](../../../install-config/high-availability.mdx).
- Worker concurrency also depends on [`AUTHENTIK_WORKER__PROCESSES`](../../../install-config/configuration/configuration.mdx#authentik_worker__processes) and [`AUTHENTIK_WORKER__THREADS`](../../../install-config/configuration/configuration.mdx#authentik_worker__threads). More replicas can use more PostgreSQL connections, but cannot resolve database or external-service bottlenecks.
- Tune `scaleDown.stabilizationWindowSeconds` to reduce replica churn. KEDA's `cooldownPeriod` applies only when scaling to zero, so it has no effect with the minimum replica counts shown here.
- The queue metric excludes tasks in progress. Scaling down can interrupt active work, and the stabilization window does not guarantee that tasks finish. Review [task time limits](../worker.mdx#time-limits) and `worker.terminationGracePeriodSeconds` (30 seconds by default) for your workload.
- Each worker metrics scrape refreshes the shared queued-task count from PostgreSQL. More worker replicas mean more scrape-time database queries. Monitor database load when scaling on this metric.
