The authentik [Helm chart](../../../install-config/install/kubernetes.mdx) can create a Horizontal Pod Autoscaler (HPA) for either the server or worker Deployment. This guide scales servers on CPU. For queue-based worker scaling, see [KEDA](./keda.mdx).

## Prerequisites

- An existing authentik Helm chart installation and its `values.yaml` file.
- A working [resource-metrics API](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/#support-for-metrics-apis) (`metrics.k8s.io`), usually provided by [Metrics Server](https://kubernetes-sigs.github.io/metrics-server/). Every container in the server pods needs a CPU request for pod CPU utilization to be defined.

## Configure the Helm chart

Merge these `server` settings into your existing `values.yaml`; keep the rest of your configuration.

```yaml title="values.yaml (excerpt)"
server:
    autoscaling:
        enabled: true
        minReplicas: 2
        maxReplicas: 5
        targetCPUUtilizationPercentage: 75
        behavior:
            scaleDown:
                stabilizationWindowSeconds: 350
    resources:
        requests:
            cpu: 500m
```

For a pod with only an authentik container requesting 500m CPU, the 75% target is 375m. Tune the CPU request, replica limits, and target for your workload.

With chart autoscaling enabled, the server Deployment omits `spec.replicas`. When switching from a fixed replica count, [this can briefly reduce the Deployment to one replica](https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/#migrating-deployments-and-statefulsets-to-horizontal-autoscaling) before the HPA reconciles it. Plan the upgrade around your availability needs.

## Deploy and verify

If switching from KEDA, remove the server ScaledObject before enabling the chart's HPA. Make the change during a quiet period and check the replica count afterward.

These commands assume a Helm release named `authentik` and a server Deployment and HPA named `authentik-server`, all in the `default` namespace. Adjust the names and namespace to match your installation.

Upgrade the release with your updated `values.yaml`, then inspect the HPA:

```shell
helm upgrade authentik authentik/authentik --namespace default -f values.yaml
kubectl get hpa authentik-server -n default
kubectl describe hpa authentik-server -n default
kubectl get deployment authentik-server -n default --watch
```

## Capacity and tuning

- Two server replicas help with [availability](../../../install-config/high-availability.mdx).
- More replicas can use more PostgreSQL connections, but cannot resolve database or external-service bottlenecks. Server capacity also depends on [`AUTHENTIK_WEB__WORKERS`](../../../install-config/configuration/configuration.mdx#authentik_web__workers) and [`AUTHENTIK_WEB__THREADS`](../../../install-config/configuration/configuration.mdx#authentik_web__threads).
- Tune `behavior.scaleDown.stabilizationWindowSeconds` to reduce replica churn. The chart also supports a worker HPA with `worker.autoscaling.enabled: true`, but CPU usage might not reflect its pending tasks.
- To scale on other signals, set `server.autoscaling.metrics` or `worker.autoscaling.metrics` and provide the corresponding Kubernetes metrics API. A nonempty `metrics` list replaces the chart-generated CPU and memory metrics, so include a CPU resource metric if you also want CPU-based scaling.
