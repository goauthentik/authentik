Consumers reference secret UUIDs through fields such as `client_secret_ref`, `admin_secret_key_ref`, or `auth_ref`. The previous string fields (`client_secret`, `shared_secret`, `bind_password`, `token`, and the like) were removed in 2026.11: create or look up a [secret](./index.mdx) and set the reference instead.

Reading a value goes through the secret's `view_value` endpoint. It takes the **View secret's value** permission and is recorded as a [`secret_view`](../events/event-actions.mdx#secret_view) event. The `rotate` endpoint replaces the value with a generated one. Updating `value` explicitly takes the same rotate permission. Both operations are audited; see [Rotate a secret](./rotation.mdx).

## Blueprints

In a [blueprint](../../customize/blueprints/index.mdx), define the secret as its own entry and reference it from the consuming object with [`!KeyOf`](../../customize/blueprints/v1/tags.mdx#keyof). For text secrets, omit `value` to have authentik generate one server-side.

**Example**:

```yaml
- model: authentik_crypto_secrets.secret
  id: my-client-secret
  identifiers:
      name: my-app client secret
- model: authentik_providers_oauth2.oauth2provider
  identifiers:
      name: my-app
  attrs:
      client_secret_ref: !KeyOf my-client-secret
```

To reference a secret that already exists, use [`!Find`](../../customize/blueprints/v1/tags.mdx#find) instead:

```yaml
- model: authentik_providers_oauth2.oauth2provider
  identifiers:
      name: my-app
  attrs:
      client_secret_ref: !Find [authentik_crypto_secrets.secret, [name, my-app client secret]]
```
