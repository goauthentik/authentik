A secret has its own permissions, separate from the provider, source, stage, or connector that uses it. This lets a team maintain an integration without giving every team member access to its password.

Assign permissions through [roles](../../users-sources/roles/index.mdx). A permission can apply to one secret or globally to all secrets. For a role responsible for one integration, assign permissions on its specific secret. A global grant also covers unrelated secrets and secrets created later.

## Choose permissions for the task

| Task                                           | Required secret permissions                                       |
| ---------------------------------------------- | ----------------------------------------------------------------- |
| Create a secret                                | **Add Secret**, granted globally                                  |
| See a secret's name and type                   | **View Secret**                                                   |
| Read, copy, or download its value              | **View Secret** and **View secret's value**                       |
| Rename it                                      | **View Secret** and **Change Secret**                             |
| Replace its value in the edit form             | **View Secret**, **Change Secret**, and **Rotate secret's value** |
| Generate a replacement using **Rotate secret** | **View Secret** and **Rotate secret's value**                     |
| Delete an unused secret                        | **View Secret** and **Delete Secret**                             |

**View Secret** reveals the secret's existence and metadata, not its value. Choose names that identify the credential without including sensitive content.

**Rotate secret's value** does not grant **View secret's value**. Someone with rotation permission can generate a replacement without receiving the new value. Grant both if they must copy the generated credential to an external system. Replacing a value through the edit form also requires **Change Secret**, because that form edits the secret object.

These permissions control access through authentik. They do not encrypt the database or restrict someone who has direct access to it. See [Secret storage](./index.mdx).

## Working with other objects

To select a secret on a provider, source, stage, or connector, you need permission to create or change that object. You also need **View Secret** to find the secret in the selector and **View secret's value** to attach it.

Attaching a credential can let an object send it to an external system. For that reason, seeing a secret's name alone is not enough to select it as a new credential.

Once an object references a secret, you can edit the object's other settings while keeping the same secret selected without permission to view the value. Changing an LDAP source's display name, for example, does not require revealing its bind password. The integration continues to use its configured secret when performing its work; individual users signing in do not need secret permissions.

Changing or rotating a secret updates every object that references it. This does not require change permission on each of those objects. Before granting rotation permission on a shared secret, consider all the integrations that depend on it.

### Example: maintain a source without reading its password

An administrator configures an LDAP source and attaches its bind password secret. A support role needs to update the source's settings while leaving the credential unchanged.

Grant the role view and change permissions on the LDAP source, and **View Secret** on its bind password secret. Keep **View secret's value** and **Rotate secret's value** unassigned. The team can recognize the configured credential and preserve the selection when saving the source. It cannot reveal, replace, or rotate that secret through the Secrets page.

Permissions on a source can still allow changes to the server that receives its credential. Review the object's own permissions when deciding whether a role should be able to change its connection settings.

### Example: maintain a shared SMTP password

Two email stages use the same SMTP account and secret. A credential-maintenance role needs to copy a replacement password from the mail service into authentik.

Grant **View Secret**, **Change Secret**, and **Rotate secret's value** on that secret. Add **View secret's value** only if the role also needs to read the stored value. Editing the shared secret updates both stages; the role does not need permission to edit either stage.

## Assign permissions on one secret

1. In the Admin interface, open **System** > **Secrets**.
2. On the secret's row, click the permissions lock icon.
3. Assign the required object permissions to the role.
4. Check the role's existing global grants and group memberships too. Removing an object grant does not cancel a global grant.

For the general permission-assignment steps, see [Manage permissions](../../users-sources/access-control/manage_permissions.mdx). A user working in the Admin interface also needs [Can access admin interface](../../users-sources/access-control/manage_permissions.mdx#assign-can-access-admin-interface-permissions).

## Access to newly created and migrated secrets

**Add Secret** does not by itself grant permission to read or manage the secret after creation. Configure [initial permissions](../../users-sources/access-control/initial_permissions.mdx) for roles that create secrets. This also matters when a provider creates a generated secret automatically. A role that creates a secret inline and then attaches it needs permission to view its value.

During upgrade, existing roles receive permission to view the secrets migrated from objects they could view or change. They retain access to credential values they could already read; previously write-only values remain hidden. Migration does not grant permission to change or rotate secrets, or access to unrelated secrets. Review these grants before delegating credential maintenance.
