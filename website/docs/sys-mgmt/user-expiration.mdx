User expiration rules automatically schedule inactive users for [offboarding](./user-offboarding.mdx) after a configurable period. You can apply a rule to a group or all users, choose whether to deactivate or delete inactive users, and warn users before their accounts expire.

## How activity is measured

Choose an **Activity basis** for each rule:

- **Last login** uses the user's recorded last login.
- **Last activity**, the default, also counts successful authentication and application access: browser, LDAP, RADIUS, and proxy authentication, OAuth client credentials with an app password, password grants, JWT client assertions, token exchanges, application authorizations, and OAuth refresh grants.

Only activity attributed to the user counts. Actions performed on another user's account and refreshes made during impersonation or a flow for a different user do not count. Failed requests, expiration warnings, background events, and API token requests also do not count. Expiration rules exclude service accounts by default.

For users with no recorded activity, the account creation date starts the inactivity period. Provisioned or invited accounts that are never used can therefore expire.

A successful OAuth refresh normally creates an activity record only once per user every 24 hours across applications. Expiration calculations add a 24-hour allowance for refresh activity, which can delay expiration by up to 24 hours. Other activity receives no allowance.

### Event retention

Event retention defaults to 365 days. For **Last activity**, retain events for at least the inactivity duration plus 24 hours. Check this setting when using long durations or shortened retention. Increasing retention does not recover deleted events, and deleting activity events can cause earlier expiration.

## Create a user expiration rule

1. In the Admin interface, navigate to **Events** > **Expiration Rules** and click **Create**.
2. Enter a **Name**.
3. Optionally select a **Group**. The rule applies to members of that group and its child groups. Leave **Group** empty to apply the rule to every user.
4. Select the **User types** to which the rule applies. Internal service accounts never expire.
5. Choose the **Activity basis** and enter the **Inactivity duration**, for example `days=90`. For **Last activity**, check that event retention covers the duration plus 24 hours.
6. Select **Deactivate** or **Delete** for the **Action**, and configure **Revoke sessions** and **Revoke tokens**.
7. Optionally enter a **Warning period**, for example `days=7`, and select the **Notification transports** used to warn the user. The warning period must be shorter than the inactivity duration.
8. Leave **Exclude superusers** enabled unless you want to include members of superuser groups.
9. Leave **Enabled** off, then click **Create**. The rule does not schedule users for offboarding until you enable it.
10. Optionally bind policies to the rule. Expand the rule's row to manage its policy bindings. The rule expires only users who pass the bound policies, so you can exempt users based on attributes or other criteria.
11. Click **Preview** to see how many users the first run would schedule for offboarding.
12. Edit the rule, turn on **Enabled**, and click **Update**. For **Delete** rules, confirm with **Save delete rule**. The rule runs immediately and every hour thereafter.

## Preview changes to a rule

Use **Preview** in the rule list to review its saved settings, or **Preview changes** in the edit form to review unsaved edits before saving. Both previews show what the rule would do if enabled and do not save changes or send warnings.

The preview separates new offboardings from pending offboardings that would be updated, taken over from another rule, or removed. For existing offboardings, it shows the action, expiration date, and session and token revocation settings before and after the change. Each section shows the total count and up to 20 users. Manual offboardings and canceled-offboarding exemptions are preserved; unchanged pending offboardings are not listed.

Delete rules require confirmation when you enable them, expand their scope, or change the activity basis, inactivity duration, warning period, or policy mode. Renaming an enabled **Delete** rule does not require confirmation.

## How rules run

Enabled rules run every hour. When a user reaches the inactivity threshold, the rule schedules an offboarding for the time of their last activity plus the configured inactivity duration. Like a [manually scheduled offboarding](./user-offboarding.mdx), it appears under **Events** > **Offboardings**. You can cancel it, and the offboarding is retried after a failure. The user's overview page shows **Cancel Expiration** and the rule that scheduled the offboarding.

If you configure a **Warning period**, the rule creates the offboarding that long before it is due, generates a **User Expiration Warning** event, and delivers the warning through the selected notification transports. If you select no transports, the warning appears as an in-app notification. Without a warning period, the rule creates the offboarding when it is due and runs it within five minutes.

A login before the scheduled time removes the pending offboarding and resets the inactivity clock. Before execution, a final check confirms that the rule still applies and that the user has reached the inactivity threshold. These checks prevent offboarding if the rule is disabled, the user's group membership changes, or the user logs in. Increasing the inactivity duration also postpones execution, even if the task is already queued.

Under **Events** > **Logs**, the **User Offboarded** event identifies the rule that triggered the offboarding.

For **Last activity** rules, activity recorded after scheduling removes the pending offboarding at the next hourly evaluation or execution check. The row can remain visible until that check. Refreshes that are not recorded because of the 24-hour interval can leave an offboarding pending, including after an activity basis change or rule takeover. Its recalculated deadline includes the refresh allowance.

## Exclusions and overlapping rules

### Excluded users

A rule skips a user when any of these conditions apply:

- The user is an internal service account.
- The user belongs to a superuser group and **Exclude superusers** is enabled.
- The user already has a pending manual or automatic offboarding.
- An automatic offboarding for the user was completed, canceled, or marked as failed on or after the user's account creation or last login, whichever is later.

A user with one of these automatic offboarding records remains exempt until their next login. This prevents a reactivated user from expiring again before they log in and become inactive. Application authorizations and OAuth refreshes do not end the exemption, and deleting activity events does not affect it. You can still schedule a manual offboarding.

### Overlapping rules

If several rules apply to the same user, the rule with the earliest expiration takes precedence. The winning rule takes over the pending offboarding, updates its date and action, and warns the user again. A final check determines the winning rule before the offboarding runs.

If two rules expire the user at the same time, a deactivation rule takes precedence over a deletion rule. If both rules use the same action, the same rule consistently takes precedence. For example, a rule that deletes contractors after 90 days does not override a rule that deactivates all users after 90 days. To delete contractors instead, exclude them from the deactivation rule with a negated group binding.

### Change or delete a rule

Editing a rule updates its pending offboardings to use the current activity basis, inactivity duration, action, and session and token revocation settings. Preview the effect before changing the activity basis. Moving expiration earlier or changing the action sends a new warning. Delaying expiration reschedules the offboarding without another warning.

Execution uses the current settings even if the next rule evaluation has not run. If a change makes the expiration immediately due, the offboarding proceeds without another warning.

Disabling a rule stops expiration and removes its pending offboardings shortly after saving. Users are not notified when these offboardings are removed. Re-enabling the rule can schedule eligible users again and send warnings according to its warning settings.

Deleting a rule removes its pending offboardings but keeps completed records in the audit history. When the action is **Delete**, the offboarding is removed with the user, so the **User Offboarded** event is the only lasting record.
