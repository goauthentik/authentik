User expiration rules automatically schedule a [user offboarding](./user-offboarding.mdx) for users who have not logged in for a configurable period. You can scope a rule to a group or to all users, choose whether inactive users are deactivated or deleted, and optionally warn users before their account expires.

## How activity is measured

A user's last activity is the later of their last login and the date their account was created. A user who has never logged in is measured from the account creation date, so accounts provisioned by a source or an invitation and never used do not stay dormant forever.

The following count as a login: browser flows, LDAP and RADIUS binds, proxy logins, and OAuth client credentials or federated token exchanges. Using an API token does not count as activity. For this reason, service accounts are excluded from expiration rules by default.

## Create a user expiration rule

1. In the Admin interface, navigate to **Events** > **Expiration Rules** and click **Create**.
2. Enter a **Name**.
3. Optionally select a **Group**. The rule applies to members of that group and of its child groups. Leave it empty to apply the rule to every user.
4. Select the **User types** the rule applies to. Internal service accounts are never expired.
5. Enter the **Inactivity duration**, for example `days=90`.
6. Select **Deactivate** or **Delete** for the **Action**, and configure **Revoke sessions** and **Revoke tokens**.
7. Optionally enter a **Warning period**, for example `days=7`, and select the **Notification transports** used to warn the user. The warning period must be shorter than the inactivity duration.
8. Leave **Exclude superusers** enabled unless you want the rule to apply to members of superuser groups as well.
9. Click **Create**.

You can also bind policies to a rule. Expand the rule's row in the list to manage its policy bindings. A user is only expired if they pass the rule's policies, which lets you exempt users based on attributes or other criteria.

Before enabling a rule, use the **Preview** action to see how many users the next run would schedule for offboarding.

## How rules run

authentik evaluates enabled rules every hour. For each user who crossed the inactivity threshold, the rule creates a pending offboarding scheduled for the user's last activity plus the inactivity duration. From that point on, the offboarding behaves like a [manually scheduled offboarding](./user-offboarding.mdx): it is listed under **Events** > **Offboardings**, it can be canceled, and it is retried on failure. On the user's page, the offboarding appears as **Cancel Expiration** and names the rule that scheduled it.

When a rule has a **Warning period**, the offboarding is created that long before the due time, and a **User Expiration Warning** event is written for the user and delivered through the selected notification transports. If no transports are selected, the user receives an in-app notification. Without a warning period, the offboarding is created when it is due and runs within five minutes.

If the user logs in before the scheduled time, the pending offboarding is removed and the inactivity clock restarts. Right before an offboarding runs, authentik re-checks that the rule still applies to the user and that the current inactivity duration has elapsed. A disabled rule, a group change, or a login that was not otherwise noticed leaves the user untouched. Extending the inactivity duration postpones execution, even if an execution task was already queued.

The **User Offboarded** event written when the offboarding runs includes the rule that scheduled it.

## Exclusions and overlapping rules

A rule skips the following users:

- Internal service accounts, always.
- Members of superuser groups, when **Exclude superusers** is enabled.
- Users who already have a pending offboarding, whether manual or automatic.
- Users whose most recent automatic offboarding is newer than their last activity. Canceling an automatic offboarding therefore exempts the user until they log in again, and a user who is reactivated after an automatic deactivation is not expired again until they log in and become inactive again.

A canceled or reactivated user who never logs in again remains exempt indefinitely. You can still schedule a manual offboarding for that user.

If several rules apply to the same user, the rule that expires them earliest wins. It takes over the pending offboarding, updates the date and action, and warns the user again. If a rule becomes less strict, for example because its inactivity duration was increased, pending offboardings are moved to the later date without a new warning.

Editing a rule also updates its pending offboardings to use the current inactivity duration, action, and session and token revocation settings. Moving the expiration earlier or changing the action sends a new warning. Execution uses the current settings even if the next rule evaluation has not run yet.

Deleting a rule removes its pending offboardings and keeps completed ones in the audit history.

## License requirements

User expiration requires a valid enterprise license. Without one, rules cannot be created or edited, no new offboardings are scheduled, and pending automatic offboardings are not executed until the license is valid again. Manually scheduled offboardings are not affected.
