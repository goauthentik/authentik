## Highlights

- **Password lockout**: :ak-enterprise Lock a user's password after a configurable number of consecutive failed login attempts.
- **User status**: The user list in the Admin interface shows a single status for each user, covering deactivated accounts and locked passwords.

## New features and improvements

### Password lockout :ak-enterprise

The [Password stage](../../add-secure-apps/flows-stages/stages/password/index.md#password-lockout) can now lock a user's password after a set number of consecutive failed attempts, using the new **Failed attempts before lockout** option. This is off by default.

A locked password is refused even when the correct password is submitted, so guessing cannot continue and a leaked password cannot be used until an administrator intervenes. The count is per user, persists across flows and sessions, and resets on a successful login.

The login prompt reports the same error it reports for a wrong password, so the response does not reveal whether an account exists or has been locked. Locking and unlocking are recorded as `password_locked` and `password_unlocked` events.

Administrators can unlock a password from the user's page in the Admin interface. Changing the password also clears the lock, so a password reset is always a way back in.

### User status

Users now expose a `composite_status` property that combines the conditions preventing a sign-in into one value: `active`, `password_locked`, or `deactivated`. It is shown in the **Status** column of the user list in the Admin interface, and is available in policies and property mappings. See [User properties and attributes](../../users-sources/user/user_ref.mdx#status).

### Passwords stored as authenticator devices

A user's password hash now lives on a password device belonging to that user, rather than in a column on the user record, which brings passwords in line with every other authenticator. Existing passwords are migrated automatically on upgrade, and no configuration changes are required.

Password devices are deliberately excluded from multi-factor authentication: they do not appear in the device APIs and cannot be selected by an authenticator validation stage.

## Upgrading

This release does not introduce any new requirements. You can follow the upgrade instructions below; for more detailed information about upgrading authentik, refer to our [Upgrade documentation](../../install-config/upgrade.mdx).

:::warning Upgrade in order and upgrade all components
Upgrades MUST be performed sequentially by major version. If you are two or more major releases behind, you must first upgrade to each intermediate major release before upgrading to this one. Refer to our [Upgrade documentation](../../install-config/upgrade.mdx) for more information on upgrade sequence.

The version of the authentik instance and of any outposts must be the same. We recommend that you always upgrade any outposts at the same time you upgrade your authentik instance.
:::

### Docker Compose

To upgrade, download the new compose file and update the Docker stack with the new version, using these commands:

```shell
wget -O compose.yml https://goauthentik.io/version/xxxx.x/lifecycle/container/compose.yml
docker compose up -d
```

The `-O` flag retains the downloaded file's name, overwriting any existing local file with the same name.

### Kubernetes

Upgrade the Helm Chart to the new version, using the following commands:

```shell
helm repo update
helm upgrade authentik authentik/authentik -f values.yaml --version ^xxxx.x
```
