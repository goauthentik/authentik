A honey user, also called a canary account or honeytoken, is a decoy account that nobody uses. Any attempt to log in as that user is a strong sign of password spraying, credential stuffing, or an attacker working through a stolen list of usernames.

authentik includes an example blueprint that creates two decoy users and a notification rule that alerts administrators when someone tries to log in as one of them.

## What the blueprint creates

The blueprint creates two users without a password. `svc-backup-admin` looks like a backup service account, and `ldap-admin` looks like a directory administrator, which attracts attackers who enumerate users through the [LDAP provider](../add-secure-apps/providers/ldap/index.mdx). No login can succeed. Each attempt fails at the password stage and creates a `login_failed` event. The response and the time it takes match those for a wrong password, so a failed attempt does not reveal that the account is a decoy.

Two [Event Matcher policies](../customize/policies/types/event-matcher.mdx) match `login_failed` and `login` events for either user. A `login` event should never happen. If one does, someone changed a decoy or linked another authentication method to it.

A [notification rule](../sys-mgmt/events/notifications.mdx) with the `alert` severity notifies the members of the configured group, `authentik Admins` by default, in the authentik UI and by email. The emails come from a dedicated transport, so their subject reads `[authentik] honey_user_login_failed`, which tells them apart from ordinary failed logins and makes them easy to filter.

The blueprint reuses `default-local-transport` and the notification group, and creates them only if they don't exist yet.

If you set `webhook_url`, the blueprint also adds a [webhook transport](../sys-mgmt/events/transports.mdx) that posts one message per event. The `text` field holds a summary in the format of Slack incoming webhooks, for example:

```text
Honey user alert: Login attempt as decoy account svc-backup-admin from 203.0.113.7 (Berlin, DE). No legitimate user owns this account.
```

The payload also carries the client IP, GeoIP and ASN data, and the user agent as separate fields for a SIEM. To change the payload for another tool, edit the `honey-user-webhook-<username>` webhook mapping under **Customization** > **Property Mappings**.

LDAP and RADIUS outposts run the authentication flow on the authentik server, so login attempts through them trigger the same alert.

## Apply the blueprint

1. Log in to authentik as an administrator and open the Admin interface.
2. Navigate to **Customization** > **Blueprints** and click **New Blueprint**.
3. Configure the blueprint instance:

    - **Name**: enter a descriptive name.
    - **Path**: select **Local path**, and then choose `example/events-honey-user.yaml`.
    - **Context**: set the decoy usernames and the group to notify, for example:

        ```yaml
        username: svc-backup-admin
        ldap_admin_username: ldap-admin
        group_name: authentik Admins
        webhook_url: https://hooks.slack.com/services/<webhook_path>
        ```

        To create only the first decoy, set `ldap_admin_username` to `""`. To skip the webhook, leave `webhook_url` empty.

4. Click **Create Blueprint**.
5. In the row of the new blueprint instance, click the **Apply** icon. Creating the instance does not apply it.

To create more decoy users, create another blueprint instance with different usernames.

## Choose a convincing decoy

- Pick a username that an attacker would want to try, such as a service, backup, or admin account, and that follows your naming convention.
- Do not reuse the username of a real or former user. Their legitimate login attempts would trigger false alerts.
- Do not set a password for a decoy. With a password, a login could succeed.
- Do not mark a decoy with attributes. Clients that can search the LDAP provider can read user attributes.
- Do not assign applications or groups to a decoy. A group named like a real administrator group could grant access in applications that read group membership.

The policies match usernames exactly. To rename a decoy, change its username in the blueprint instance context instead of editing the user, apply the blueprint again, and then delete the old user. If you change `username`, also delete the old `honey-user-*` objects, which otherwise keep sending alerts.

## Plant the decoy

To catch attackers who are already inside your network, leave the decoy's username, with a made-up password, where they look for credentials: a script or configuration file on a file share, an internal wiki page, or a test entry in a password manager. Because the decoy has no password, any attempt fails and triggers the alert, whatever password the attacker tries.

- Use a made-up password that is not used anywhere else.
- Do not plant decoys in public places, such as public repositories. Automated scanners would trigger alerts that don't point to a real intrusion.

## Limitations

- The alert covers login attempts that reach the password stage. Flows that skip the password stage, for example passwordless or source logins, do not create a `login_failed` event for this user.
- With an LDAP provider in [cached bind mode](../add-secure-apps/providers/ldap/index.mdx#cached-bind), the outpost answers repeated binds with the same DN and password from its cache. Only the first attempt with each password creates an event.
- [Password lockout](../add-secure-apps/flows-stages/stages/password/index.mdx#password-lockout) never applies to a decoy, so a decoy never shows a last-attempt warning or lockout message.
- Honey users cover login attempts only, not API tokens or other credentials.
