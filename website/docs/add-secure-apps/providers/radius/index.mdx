The RADIUS provider allows applications and network devices to authenticate users through authentik using RADIUS. It supports password-based authentication with PAP and certificate-based authentication with EAP-TLS in authentik Enterprise. Only authentication requests are supported; accounting requests are not supported.

Refer to [Create a RADIUS provider](./create-radius-provider.mdx) for instructions on creating, deploying, and testing the provider.

## Authentication flow

Authentication requests against the Radius Server use a flow in the background. This allows you to use the same flows, stages, and policies as you do for web-based logins.

The following stages are supported:

- [Identification stage](../../flows-stages/stages/identification/index.mdx)
- [Password stage](../../flows-stages/stages/password/index.mdx)
- [Authenticator validation stage](../../flows-stages/stages/authenticator_validate/index.mdx)
- [User logout stage](../../flows-stages/stages/user_logout/index.mdx)
- [User login stage](../../flows-stages/stages/user_login/index.mdx)
- [Deny stage](../../flows-stages/stages/deny/index.mdx)
- [Mutual TLS stage](../../flows-stages/stages/mtls/index.mdx) (authentik Enterprise, for EAP-TLS)

Include a user login stage to complete authentication. After authentication, authentik checks whether the user can access the associated application. Application [bindings](../../applications/manage_apps.mdx#use-bindings-to-control-access) can restrict which users are allowed access.

### Code-based MFA support

For PAP authentication, the provider supports appending a TOTP or static code to the password when **Code-based MFA Support** is enabled and the authentication flow includes an authenticator validation stage.

Separate the password and code with a semicolon. For example, for the password `example-password` and the MFA code `123456`, enter `example-password;123456`.

:::warning Passwords containing semicolons
When **Code-based MFA Support** is enabled, the outpost splits the password at the last semicolon if it is followed by a value. This can cause a password containing a semicolon to be rejected when the user does not append an MFA code. Disable this setting if you do not use the appended-code format.
:::

:::info Authenticator support
The authenticator validation stage supports Duo, TOTP, and static authenticators in RADIUS flows. WebAuthn and SMS-based authenticators are not supported by the RADIUS outpost's flow executor.
:::

### EAP-TLS :ak-enterprise {#eap}

EAP-TLS uses certificates to authenticate the server and client. Before configuring the provider, obtain a server certificate and private key, a certificate authority (CA) certificate for validating clients, and client certificates and private keys for the end-user devices. Certificate issuance and deployment are outside the scope of this document.

1. Create an authentication flow with a [mutual TLS stage](../../flows-stages/stages/mtls/index.mdx) as its first stage.
    - Set **Mode** to **Required**.
    - Under **Certificate authorities**, select the CA certificates that should be trusted to issue client certificates.
    - Configure **Certificate attribute** and **User attribute** so that the certificate identifies an existing authentik user.
2. Add a user login stage after the mutual TLS stage to complete authentication.
3. In the RADIUS provider, set **Authentication Flow** to this flow and select the server certificate under **Protocol settings** > **Certificate**. The certificate must have its private key available to the outpost.
4. Configure the end-user devices to use their client certificates and validate the RADIUS server certificate, including the expected server name and trusted issuing CA.

:::warning Limit trust for client certificates
Use a private CA whose client-certificate issuance you control. The mutual TLS stage validates the certificate against its configured CAs and matches a certificate attribute to an existing user; trusting a CA alone does not authorize every certificate holder. Ensure that certificate holders cannot obtain certificates identifying other users, and use application bindings or additional policies to restrict access as needed.

The CAs trusted by the mutual TLS stage for client authentication are separate from the CA that end-user devices trust for the RADIUS server certificate.
:::

## RADIUS property mappings {#radius-attributes}

RADIUS provider property mappings add attributes to successful authentication responses. A single mapping can assign multiple attributes. Follow the instructions to [create a custom provider property mapping](../property-mappings/index.mdx#create-a-custom-provider-property-mapping), selecting the RADIUS provider property mapping type. Then select the mapping under **Protocol settings** > **Property mappings** on the RADIUS provider.

### Mapping context

Mappings run after authentication and application authorization succeed. They supply attributes for the `Access-Accept` response and cannot customize an `Access-Reject`, including its `Reply-Message`.

The mapping receives:

- `user`: the authenticated user, through which you can access user attributes and group memberships.
- `packet`: a mutable packet used to build additional response attributes. It is not the incoming `Access-Request` or the final `Access-Accept`; the outpost copies its attributes into the successful response.

Incoming RADIUS attributes are not forwarded into the mapping context. The HTTP request available to the expression is the outpost's access-check request to authentik, not the incoming RADIUS packet.

Mappings run in name order and modify the same `packet` in place. Their return values are ignored; returning a dictionary or a replacement packet does not add attributes to the response.

### Standard attributes

Use the attribute's exact name from authentik's [bundled RADIUS dictionary](https://github.com/goauthentik/authentik/blob/main/authentik/providers/radius/dictionaries/dictionary).

The following example adds three standard attributes in a single mapping: an integer `Session-Timeout`, a string `Reply-Message`, and an `octets` value for `Class`. All three are already defined in the bundled dictionary, so no `define_attribute()` calls are needed.

```python
packet["Session-Timeout"] = 3600
packet["Reply-Message"] = "Network access granted"
packet["Class"] = b"authentik-radius"
```

These assignments modify the supplied packet, so no return statement is required. The `Reply-Message` is added only to a successful response; it does not configure a rejection message. The `Class` value is a fixed example marker, not a unique session identifier.

After assigning the mapping to the provider, authenticate and inspect the decoded `Access-Accept`. Confirm that all three values appear as standard attribute codes `27` (`Session-Timeout`), `18` (`Reply-Message`), and `25` (`Class`), not as vendor-specific attributes. The `Class` bytes should represent the literal text `authentik-radius`.

An attribute appearing in a vendor dictionary does not guarantee that it is present in authentik's bundled dictionary. The Python value must also match the attribute's dictionary type.

### Vendor-specific attributes

For a vendor-specific attribute already defined in a bundled dictionary, use its existing name. For example, the bundled Cisco dictionary defines vendor code `9`, attribute code `1`, under the name `AVPair`:

```python
packet["AVPair"] = "shell:priv-lvl=15"
```

To register a new lookup name, use `define_attribute()` before assigning a value. The following alternative registers `Cisco-AV-Pair` for the same vendor-specific attribute and assigns the same privilege level:

```python
define_attribute(
    vendor_code=9,
    vendor_name="Cisco",
    attribute_name="AV-Pair",
    attribute_code=1,
    attribute_type="string",
)

packet["Cisco-AV-Pair"] = "shell:priv-lvl=15"
```

| Argument         | Description                                                  |
| ---------------- | ------------------------------------------------------------ |
| `vendor_code`    | The vendor's IANA Private Enterprise Number                  |
| `vendor_name`    | The vendor name used to qualify the attribute in the mapping |
| `attribute_name` | The attribute name to register                               |
| `attribute_code` | The attribute number from the vendor's RADIUS dictionary     |
| `attribute_type` | The dictionary value type, such as `string` or `integer`     |

Use codes and types from authoritative vendor documentation. The registered lookup name is `<vendor_name>-<attribute_name>`. Definitions are shared by mappings for the current access check but do not permanently change the bundled dictionary. If that lookup name already exists, the helper leaves its definition unchanged.

You can call `define_attribute()` multiple times in one mapping to register different attributes, then assign their values to `packet`. Each definition and value must still be valid; a mapping evaluation error stops processing and omits all mapping-generated attributes, as described in [Troubleshoot a failed mapping](#troubleshoot-a-failed-mapping).

Do not assign a vendor name to a standard RFC attribute: a nonempty `vendor_name` produces a Vendor-Specific attribute, even if `vendor_code` is `0`.

### Attribute value types

Common dictionary types accept the following values. Encoding is handled by [pyrad](https://github.com/wichert/pyrad/blob/2.5.4/pyrad/tools.py), the RADIUS library used by authentik.

| Dictionary type | Example Python value | Notes                                                                                            |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------------ |
| `string`        | `"example"`          | Strings are UTF-8 encoded.                                                                       |
| `integer`       | `3600`               | Use an unsigned 32-bit integer, or a symbolic value defined for the attribute in the dictionary. |
| `ipaddr`        | `"192.0.2.10"`       | Use an IPv4 address string for an IPv4 attribute.                                                |
| `octets`        | `b"session-id"`      | Use bytes for an opaque value; see the encoding caveat below.                                    |

For `octets`, pyrad treats strings containing only decimal digits as integers to encode, rather than literal text. For example, `"65"` becomes `b"A"`, while `b"65"` preserves the two ASCII digits. Values beginning with `0x`, including bytes beginning with `b"0x"`, are interpreted as hexadecimal. Inspect the decoded response when the exact byte representation matters.

### Dynamic VLAN assignment

The bundled dictionaries do not define `Tunnel-Type`, `Tunnel-Medium-Type`, or `Tunnel-Private-Group-Id`, so these names cannot be assigned directly using the standard-attribute example above. This dictionary limitation does not by itself establish whether the underlying encoder can represent those attributes.

Dynamic VLAN configuration also requires the correct attribute types and tunnel-tag encoding. Do not substitute similarly named vendor-specific attributes for standard tunnel attributes unless the client explicitly expects them. See [#16879](https://github.com/goauthentik/authentik/issues/16879) and [#25324](https://github.com/goauthentik/authentik/issues/25324) for related discussion.

### Troubleshoot a failed mapping

:::warning Mapping errors do not necessarily deny access
A mapping evaluation error stops mapping processing and omits all mapping-generated response attributes, including those added by earlier mappings. It does not itself change a successful authorization result. Do not rely on a mapping failure to deny access; use application bindings or authentication policies for access control.
:::

If the expected attributes are missing:

1. Confirm that authentication and application authorization succeeded.
2. Confirm that the mapping is selected on the provider.
3. Check the attribute name and capitalization against the bundled dictionary or the name registered with `define_attribute()`.
4. Confirm that each value matches the attribute's dictionary type.
5. In the Admin interface, check **Events** > **Logs** for a configuration-error event. Also check the server and outpost logs for packet serialization or decoding failures.
6. Inspect the decoded `Access-Accept` to verify the attribute codes, vendor codes, values, and any required tags.

For an end-to-end check, follow [Configuration verification](./create-radius-provider.mdx#configuration-verification).
