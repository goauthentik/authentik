---
title: OAuth source
---

This source allows users to enroll themselves with an external OAuth-based identity provider. The generic provider expects the endpoint to return OpenID Connect-compatible information. Vendor-specific implementations have their own OAuth source.

- Policies: Allow/Forbid users from linking their accounts with this provider.
- Icon: Optional icon or image shown for the source. See [File picker values](../../../../customize/file-picker.mdx).
- Request Token URL: This field is used for OAuth v1 implementations and will be provided by the provider.
- Authorization URL: This value will be provided by the provider.
- Access Token URL: This value will be provided by the provider.
- Profile URL: This URL is called by authentik to retrieve user information upon successful authentication.
- Consumer key/Consumer secret: These values will be provided by the provider.
- Scopes: Configure additional scopes to send to the provider.

    Starting with authentik 2022.10, the default scopes can be replaced by prefixing the value for scopes with `*`.

- Forward query parameters: A comma-separated list of query parameter names that authentik forwards to the upstream identity provider's authorization URL. Parameters that aren't in the list are ignored.

    authentik forwards matching parameters in two cases:
    - When a user opens the source login URL directly, for example `https://authentik.company/source/oauth/login/my-source/?idphint=urn:mace:incommon:uiuc.edu`.
    - When a user clicks the source's button during an authentication flow. In this case, authentik forwards matching parameters from the request that started the flow, such as an application's request to authentik's OAuth2/OpenID `/authorize` endpoint.

    Use this setting to pass provider-specific hints to the upstream provider. For example, set the field to `idphint` so that [CILogon](https://www.cilogon.org/oidc) skips its own selection screen and sends users directly to their institution's login page.

    Another example is to set the field to `prompt`. An application can then send `prompt=select_account` to authentik's `/authorize` endpoint, and authentik forwards the value unchanged to an upstream provider such as Google, which then shows its account chooser. This is useful when enrollment is disabled: users who logged in with the wrong upstream account can choose a different one, instead of being logged in with the same account again. authentik doesn't handle `select_account` itself, and only forwards it when the user has to log in to authentik through the source.

    authentik sets the parameters `client_id`, `redirect_uri`, `response_type`, `scope`, `state`, `code_challenge`, and `code_challenge_method` itself, so they can't be forwarded.

## OpenID Connect

### Well-known

Instead of configuring the URLs for a source manually, if the application you're configuring implements the [OpenID Connect Discovery Spec](https://openid.net/specs/openid-connect-discovery-1_0.html), you can configure the source with a single URL. The URL should always end with `.well-known/openid-configuration`. Many applications don't explicitly mention this URL, but for most of them it will be `https://application.company/.well-known/openid-configuration`.

This URL is fetched upon saving the source, and all the URLs will be replaced by the ones from the Discovery document. No automatic re-fetching is done.

### JWKS

To simplify machine-to-machine authentication, you can create an OAuth source as a trusted source of JWTs. Create a source and configure either the Well-known URL or the OIDC JWKS URL. You can also manually enter the JWKS data.

Afterward, this source can be selected in one or more OAuth 2.0 providers. Any JWT issued by the configured source's JWKS can authenticate. To learn more about this, see [JWT authentication](../../../../add-secure-apps/providers/oauth2/machine_to_machine#jwt-authentication).

### `login_hint` parameter

If the OAuth authentication was started from within an authentik flow and the user has already identified themselves, authentik will set the `login_hint` parameter to the email address of the user. If the Identification stage has the **Pretend user exists** option enabled and a user could not be found, the `login_hint` value will be set to the identifier that the user entered.

## OAuth source property mappings

See the [overview](../../property-mappings/index.mdx) for information on how property mappings work.

### Expression data

The following variables are available to OAuth source property mappings:

- `info`: A Python dictionary containing OAuth claims. For example (values might differ depending on the source):
    ```python
    {
        "iss": "https://source.company",
        "sub": "f153e7da687eec8c8789c72b6cc6bb5197df7b48b263b3151f36908e1bc10691",
        "aud": "01e4DmQiG1d3kaewD3Mkz7E7kXknk9j43eZMkNaE",
        "aud": "a7809c1b1c4aaa50adfb68660a6273dd9c8d15e4",
        "email": "user@authentik.company",
        "email_verified": True,
        "name": "User",
        "given_name": "User",
        "preferred_username": "user",
        "nickname": "user",
    }
    ```
- `client`: An OAuth client object to make requests to the Source with authentication built-in.
- `token`: A Python dictionary containing OAuth tokens.
