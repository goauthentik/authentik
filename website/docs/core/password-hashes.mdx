---
title: Password hashes
description: Generate and import encoded password hashes in authentik.
---

authentik uses [Django's encoded password format](https://docs.djangoproject.com/en/stable/topics/auth/passwords/#how-django-stores-passwords) for local passwords. Importing a hash sets only the local verifier; it cannot update LDAP or Kerberos because authentik does not receive the raw password.

## Generate a password hash

Run `hash_password` with the target authentik version so that its [work factors](https://docs.djangoproject.com/en/stable/topics/auth/passwords/#increasing-the-work-factor) and [salt entropy](https://docs.djangoproject.com/en/stable/topics/auth/passwords/#increasing-the-salt-entropy) match the bundled Django configuration. Use the complete output.

```bash
docker compose run --rm server hash_password
```

For non-interactive use:

```bash
printf '%s\n' "$PASSWORD" | docker compose run --rm -T server hash_password
```

## Password hash import settings

Bootstrap imports and API imports without an override accept `pbkdf2_sha256`, `argon2`, `bcrypt_sha256`, and `scrypt`. Parameters and salt entropy must match the target authentik version's bundled Django configuration.

Django estimates salt entropy as `length * log2(62)`. A salt generated with a different alphabet can therefore be rejected even when its actual entropy is sufficient.

These settings do not affect stored hashes; supported legacy hashes such as `pbkdf2_sha1` continue to verify.

## Import plain bcrypt hashes

Plain bcrypt hashes, as written by Ruby on Rails (Devise, `has_secure_password`) and other bcrypt-based applications, can be imported with `override=true`. Prefix the existing hash with `bcrypt$`:

```text
$2a$12$mnMJ7Lw1LUvjquNPgibslO8ividA5GNMa6uEVWVEutyDm6OxNdTtq
bcrypt$$2a$12$mnMJ7Lw1LUvjquNPgibslO8ividA5GNMa6uEVWVEutyDm6OxNdTtq
```

The first line is the original hash, the second line is the value to import. authentik verifies these hashes but never creates new ones with this hasher. After a successful login, the password is rehashed with the default hasher.

The original application must not use a pepper or pre-hash the password before bcrypt. Like most bcrypt implementations, authentik only considers the first 72 bytes of a password when verifying these hashes. After the upgrade on login, the new hash covers the full password.

## Import paths

- [`AUTHENTIK_BOOTSTRAP_PASSWORD_HASH`](../install-config/automated-install.mdx#authentik_bootstrap_password_hash) applies these settings during the first startup and has no override. A rejected hash stops initial setup.
- The [`set_password_hash` API endpoint](/api/reference/core-users-set-password-hash-create) applies these settings by default. `override=true` accepts any configured hash that authentik can decode and records the override in the password-set event.
- Blueprint [`password_hash`](../customize/blueprints/v1/models.mdx#password_hash) values are stored as supplied without applying these settings.
